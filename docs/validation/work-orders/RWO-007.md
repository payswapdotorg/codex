# RWO-007 — Upgrade Means Forward: Ordering + Downgrade + Rollback Direction Semantics (FlowMart)

**Status:** PROPOSED (VWO-010 synthesis)
**Priority:** P1 (Family G, product half) + P2 rider (Family M)
**Closes (canonical):** Family G product half (VWO-009 F4) and Family M (VWO-009 F5).
NOTE: the engine half of Family G (decide_upgrade ordering in
codex-workflow-distribution) is RWO-009's rider — the Tech Lead may dispatch
both together or separately; surfaces and owners are disjoint.
**Depends on:** none

## Objective

Make version-movement semantics honest at the FlowMart product layer:
"upgrade" only moves the pin forward (or is an explicitly labeled downgrade);
"rollback" only moves it backward; neither can mislabel its effect.

## Findings closed

- VWO-009 F4 (P1, product half): `upgradeInstall` accepted target 1.3.0 →
  1.2.0 recorded as "upgraded" — no ordering/explicit-downgrade guard.
- VWO-009 F5 (P2): after a downgrade-as-upgrade, `rollbackInstall` selected
  "the last history entry whose toVersion differs from the current pin" —
  the NEWER version — and moved the pin FORWARD labeled "rolled back".

## Fix scope (bounded)

`docs/validation/fixtures/marketplace/ops-install.js`:

1. `upgradeInstall` (~117): add a semver-ordering comparison between
   `targetVersion` and `inst.version`. Older target → HTTP 409
   `implicit_downgrade_refused` telling the user to use the rollback op
   (or an explicit `downgrade: true` flag if the Tech Lead wants a labeled
   downgrade path — smallest fix: refuse).
2. `rollbackInstall` (~156): derive the rollback target from the most recent
   `upgraded` history entry's `fromVersion` (not "any toVersion differing from
   current") — rollback then always moves backward to the version the pin
   came from; no prior upgrade → existing "no prior version" error unchanged.
3. Update `FAILURES.md` with both contracts.

## Acceptance criteria

1. Upgrade with an older target → 409 `implicit_downgrade_refused`; pin, 
   history, events unchanged.
2. After a legit upgrade 1.2.0 → 1.3.0, rollback → 1.2.0 (the upgrade's
   fromVersion) — never forward.
3. Duplicate-version and stale-pin rejections unchanged (VWO-005/006 paths
   still pass).
