# RWO-011 — Rejection/Conflict Audit Events in the Shared Fixture Runtime

**Status:** PROPOSED (VWO-010 synthesis)
**Priority:** P2 (Family J — confirmed by three independent reports)
**Closes:** VWO-007 F2, VWO-008 F6, VWO-009 F3 (repelled/blocked operations
leave NO audit events).
**Depends on:** none

## Objective

Make every repelled dedup/conflict/permission rejection durably auditable:
the event feed must record that an attack or race was attempted and repelled,
not only the successes.

## Findings closed

- VWO-007 F2 (P2): dedup rejections invisible to the audit trail — the
  two-tab duplicate, 7 storm rejections and post-restart replays recorded
  nothing; a later auditor must trust the actor's transient 409.
- VWO-008 F6 (P2): same in the approval context (losing race submissions,
  stale re-submissions, permission-denied probes — zero events).
- VWO-009 F3 (P2): same in the distribution context (503 upgrade rejection,
  stale_entitlement blocks, data_conflict rejections).

## Reproduction evidence

The three reports' event-feed pulls (VWO-007 adv-duplicate-triggers post-hoc
event-continuity evidence; VWO-008 adv-approval-race evidence; VWO-009
adv-environment-failure-rebinding post-hoc battery). VWO-010's own batteries
re-confirmed the pattern incidentally: the Family E/G/H probes' rejections
produced no events (only the successes appear in `/api/events`), consistent
with the shared runtime emitting only on successful mutations.

## Fix scope (bounded)

`docs/validation/fixtures/_lib/runtime.js` (shared request pipeline):

- On `AppError` with status 409/403 (the dedup/conflict/permission path —
  NOT validation 400s), emit a typed rejection event
  (e.g. `request.rejected` with `{ op, code, actor, subject }`), before the
  error propagates. One emit site in the shared error path covers all five
  apps; per-app op names already flow through the pipeline context.
- Keep the idempotency-dedup ledger behavior unchanged (VWO-007's guarantees
  must not regress); the rejection event is additive.
- Update the fixtures README event vocabulary.

## Acceptance criteria

1. Re-run adv-duplicate-triggers: the two-tab duplicate and each storm 409
   produce `request.rejected` events naming the op and code.
2. Re-run VWO-008 adv-approval-race: the losing submission, stale replay and
   permission-denied probes appear in the feed.
3. Re-run VWO-009 blocked operations: 503-refused upgrade, stale_entitlement
   blocks and data_conflict rejections appear.
4. `verify-sweep.sh` → 59/59 (the sweep's 409 switch probes will now also
   produce rejection events — assertions that count events exactly must be
   updated if any exist; check the sweep script before merging).
