# RWO-001 — Mount the Workflow/Teaching Control Plane Behind User-Facing Surfaces

**Status:** PROPOSED (VWO-010 synthesis; Tech Lead reviews, amends, dispatches)
**Priority:** P0 — the single root finding of the entire validation program
**Closes (canonical):** Family A (VWO-004 F1 · VWO-005 F1 · VWO-006 F-1 · VWO-007 F1 · VWO-008 F1 · VWO-009 F1)
**Depends on:** none (this unblocks RWO-005, RWO-006, RWO-014, RWO-015)

## Objective

Give a normal person a real product surface for the workflow plane that today
exists only as library crates: teach (DEMONSTRATE / INSTRUCT / HYBRID) →
compile → review → approve → publish an immutable version, then operate the
durable instance lifecycle (list with status/position, run, pause, resume,
cancel) with Workflow Identity fields (version, definition digest,
dependency-lock identity) visible at every step.

## Findings closed

- VWO-004 F1 (P0) — teaching surface absent, all 12 scenarios, 4th confirmation.
- VWO-005 F1 (P1) — teach/compile/review/approve absent product-wide.
- VWO-006 F-1 (P1) — workflow-consumer product surface absent.
- VWO-007 F1 (P1) — durable control plane unmounted (instance/recovery surfaces).
- VWO-008 F1 (P1) — trust-boundary guarantees unobtainable by a normal person.
- VWO-009 F1 (P1) — versioning/distribution guarantees unmounted.

## Fix scope (bounded)

- `codex-rs/app-server-protocol` — NEW additive protocol methods (names TBD by
  the Tech Lead; suggested prefix `workflow/`): teaching-session
  (start/instruct/demonstrate/reconcile), compile, review, approve, publish;
  instance list/get/resume/cancel; identity fields on every response.
- `codex-rs/app-server` — handlers delegating to `codex-workflow-app` /
  `codex-teaching-compiler` / `codex-workflow-durable` ports (in-memory doubles
  first; durable wiring already exists from MWO-001).
- `codex-rs/cli` — one `workflow` subcommand group surfacing the same methods.
- NO new engine semantics: this WO mounts existing ports only (VALIDATION-PROGRAM.md
  §11 "prefer fixing existing contracts/integration seams").
- Forbidden: parallel orchestration runtime; UI-owned durable state; bypassing
  approvals/sandboxing/policy; silent workflow-version mutation (per WO-010
  implementation WO's Forbidden list, which this WO inherits).

## Acceptance criteria

1. A person with no internals knowledge can, through CLI or app-server client:
   teach a workflow in each of the three modes, compile it, review/approve,
   publish immutable v1, and observe version + digest + lock identity.
2. Durable instances appear in a list with status/position; resume and cancel
   are explicit; a kill/restart of the process preserves them (VWO-007
   acceptance question becomes answerable at the product layer).
3. Ordinary Codex coding-agent behavior is unchanged when no workflow is used.
4. Zero changes to frozen engine semantics (contracts/forge/distribution code
   untouched except wiring).

## Rollback

The mount is additive (protocol methods + CLI subcommands + handler wiring).
Revert the single merge commit; engine crates are untouched, so no data/state
migration is involved.

## Size estimate

integration tests ~6. Engine code: 0 lines (ports already exist).
