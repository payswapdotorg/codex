# RWO-009 — Engine Distribution: Visibility Gate on the Upgrade Path (+ Ordering Guard Rider)

**Status:** PROPOSED (VWO-010 synthesis)
**Priority:** P1 (Family I) + P1 rider (Family G engine half)
**Closes (canonical):** Family I (VWO-009 F10) and the engine half of Family G (VWO-009 F4).
NOTE: the product half of Family G is RWO-007 — disjoint surface/owner; the
Tech Lead may dispatch together or separately.
**Depends on:** none (engine crate fix; independent of the RWO-001 mount)

## Objective

Restore the documented gate order (visibility → integrity → access →
entitlement) on the upgrade evaluation/approval path in
`codex-workflow-distribution`, and make `decide_upgrade` refuse targets that
are older than the installed pin.

## Findings closed

- VWO-009 F10 (P1): `evaluate_upgrade` surfaced a PRIVATE release's identity
  to a non-owner installer and `decide_upgrade` APPROVED and applied it —
  the visibility gate that search and direct install enforce is skipped on
  the upgrade path (cross-owner private-release leakage; WO attack 6
  succeeded at the engine layer).
- VWO-009 F4 (P1, engine half): the follow/apply path applied a target OLDER
  than the installed pin via an upgrade record (engine probe: 2.0.0 → 1.5.0).

## Fix scope (bounded)

`codex-rs/workflow-distribution/src/memory.rs` (+ unit tests in the crate):

1. `evaluate_upgrade`: filter candidate entries through the same visibility
   predicate `install` uses (`release_installable(&entry.metadata, entry.state,
   &entry.audience, &requesting principal)` — the principal is the install's
   owner); private releases are invisible to foreign installers.
2. `decide_upgrade`: before approval, re-run the visibility gate on the target
   entry (documented order: visibility → integrity → access → entitlement) —
   foreign/private targets → `ReleaseNotVisible`.
3. Ordering guard (Family G engine half): reject an upgrade proposal whose
   `to` version is older than `from` with a typed error (e.g.
   `IllegalDowngrade { expected_newer_than, got }`), unless the Tech Lead
   opts for an explicit `explicit_downgrade` decision variant — smallest fix:
   refuse.

## Acceptance criteria

1. Engine attack 6d re-run: foreign installer's `evaluate_upgrade` returns
   None (or a not-visible refusal); `decide_upgrade` on a smuggled proposal →
   `ReleaseNotVisible`; pin unchanged.
2. Engine attack 12 re-run: older-target upgrade record → refused with the
   typed downgrade error; pin unchanged.
3. All existing distribution tests still pass (search/install visibility,
   gate order, stale-proposal, AlreadyInstalled).
