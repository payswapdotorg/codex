# WO-005 — Multi-Environment Execution Contract

**Status:** MERGED (PR #4, bf7245c1)
**Depends on:** WO-003
**Surface:** new workflow execution/capability/resource contracts and adapters boundary

## Objective

Create one execution abstraction capable of routing workflow steps across Codex-native and external environments without duplicating the workflow engine.

## Required outcomes

- Define `ExecutionEnvironment`, `EnvironmentAdapter`, `CapabilityBinding`, `ResourceBinding`, `Observation`, `Action`, `ActionResult`, `Recovery`, and takeover contracts.
- Model `BROWSER`, `COMPUTER`, `TERMINAL`, `API`, `TOOL`, `MCP`, and `HUMAN` as peer environments.
- Reserve `MOBILE`, `REMOTE_DESKTOP`, and future environments without semantic changes.
- Support mixed-environment workflows within one graph/run.
- Make required capability/environment availability diagnosable and policy-controlled.
- Reuse Codex approvals, sandboxing, skills, plugins, MCP, sessions, traces, and agent primitives where applicable.
- Define readiness explicitly as `DECLARED -> AVAILABLE -> READY -> AUTHORIZED -> BOUND -> EXECUTING`, with `FAILED`/`UNAVAILABLE` diagnostics.
- Permit fallback only when semantic requirements and policy remain satisfied; record selected binding and fallback reason as evidence.

## Must inspect before coding

- current Codex executor/tool interfaces and environment execution paths
- Browser Use and Computer Use requirements/configuration surfaces
- terminal/tool/MCP invocation abstractions
- skills/plugins/subagent/planning/approval/sandbox/session/trace primitives
- existing worktree/remote-control abstractions where they can satisfy future environment needs

## Forbidden

- Implementing browser or computer runtime internals in this Work Order.
- Creating a second workflow engine.
- Hard-coding GitHub or a model provider.
- Making UI state the source of durable execution semantics.

## Acceptance

The same workflow step semantics can bind to different compatible environments; one execution can contain multiple environments; unavailable required capabilities fail explicitly; fallback is policy/contract checked and evidenced; no environment adapter becomes semantic authority.

## Evidence

Report final contract/type inventory, readiness/fallback behavior, environment matrix, capability/resource separation, adapter conformance tests, and exact verified SHA.
