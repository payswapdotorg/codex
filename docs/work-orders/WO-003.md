# WO-003 — Git-Native Workflow Contracts

**Status:** MERGED
**Depends on:** WO-001
**Surface:** new workflow contracts/control-plane interfaces and repository/domain types

## Objective

Define workflows as first-class Git-native software artifacts while keeping semantic authority in the workflow control plane.

## Required outcomes

- Define `WorkflowRepository`, `WorkflowManifest`, `WorkflowIR`, `WorkflowDefinition`, immutable `WorkflowVersion`, `WorkflowInstance`, capability/resource requirements, roles, triggers, dependency locks, and evidence references.
- Define immutable source revision + semantic version + dependency identity as execution version identity.
- Define fork/branch/review/release concepts without making GitHub the semantic authority.
- Define explicit subworkflow dependencies and version pinning.
- Define skill/plugin/MCP dependencies separately from workflow semantics.
- Separate development refs from executable immutable revision identity.
- Preserve provenance/attribution/license/upgrade-policy fields without embedding commercial settlement or credentials in workflow semantics.

## Must inspect before coding

- existing `codex-rs/git-utils` and worktree abstractions
- Git/worktree metadata and repository identity handling
- existing app-server/protocol domain conventions for versioned durable records
- `payswapdotorg/workflows` only as a semantic reference, never as runtime authority
- current source/test conventions for new Rust contracts and serialization

Do not implement GitHub API calls here. Define forge-neutral contracts that WO-009 can bind to GitHub.

## Forbidden

- UI implementation.
- GitHub-only semantic types.
- Browser/computer runtime implementation.
- Payment or marketplace implementation.
- Durable control-plane implementation beyond the contracts/interfaces required by this Work Order.

## Acceptance

A workflow can be represented, versioned, composed, and instantiated without depending on a specific environment, model provider, or UI. Published versions cannot be mutated by moving branches or agent actions. Subworkflow and capability dependencies have explicit identity/provenance and can be locked independently.

## Evidence

Report final contract/type inventory, immutability/version identity rules, forge abstraction boundary, dependency-lock model, serialization tests/invariants, and exact verified SHA.
