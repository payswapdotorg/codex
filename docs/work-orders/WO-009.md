# WO-009 — Git-Native Workflow Collaboration

**Status:** MERGED (PR #9, e84e9da7c)
**Depends on:** WO-003, WO-005
**Surface:** workflow repository/forge integration and composition model

## Objective

Make workflows behave like software repositories: collaborative, forkable, branchable, reviewable, composable, version-pinned, publishable, and installable from the Codex application.

## Required outcomes

- Define `WorkflowRepository` over a forge-neutral contract with GitHub as the first adapter.
- Support repository discovery, clone/fetch, fork metadata, branches, commits, pull requests, review, merge, release/tag, and immutable source revision resolution.
- Define workflow-package manifest and dependency lock semantics.
- Support subworkflow dependencies pinned to immutable versions/revisions.
- Support workflow fork lineage and attribution.
- Separate development refs from published/executable immutable versions.
- Make installed workflow updates explicit and reviewable.
- Preserve workflow semantic authority in the workflow control plane rather than GitHub.

## Forbidden

- Hard-coding workflow semantics to GitHub APIs.
- Executing moving branches as published workflow versions.
- Importing credentials from repositories.
- Creating a separate collaboration/workflow engine outside the Codex app/runtime.

## Acceptance

Two users can independently change a workflow through branches/forks, review and merge changes, publish an immutable release, and install or upgrade it without silently changing existing running instances. A workflow can depend on another workflow using a pinned immutable revision.
